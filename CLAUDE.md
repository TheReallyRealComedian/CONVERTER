# CONVERTER — Multimedia Converter & Narration

## What is this?
Flask web app for multimedia conversion: Markdown-to-PDF, document-to-Markdown, audio transcription (Deepgram), and faithful document narration (Google Cloud TTS with Gemini-TTS voices). Runs in Docker with Redis/RQ for background jobs. Single-User-App (nur Oliver), LAN-only, login-protected.

## Tech Stack
- **Backend**: Flask (async), SQLAlchemy (SQLite), Flask-Login
- **Job Queue**: Redis + RQ (worker container for narration rendering)
- **APIs**: Deepgram (transcription), Google Cloud TTS (Gemini-TTS voices → faithful narration), Gemini API (`gemini-2.0-flash` in `pdf_extraction` — separates Feature; `GEMINI_API_KEY` weiterhin nötig)
- **Frontend**: Bootstrap + vanilla JS (Jinja2 templates)

## Key Files
- `app.py` — Bootstrap shim (~70 LOC); imports `app_pkg`, holds service singletons that tests patch at `app.<name>`
- `app_pkg/` — App factory + per-feature route modules (auth, library, markdown, documents, audio, narration, mermaid, `integrations/notion`). Each module exposes a `register(app)` function; **no Flask `Blueprint(...)`** — endpoint names stay flat so templates' `url_for("login")` etc. don't need rewrites
- `app_pkg/config.py` — Shared constants (e.g. `OUTPUT_DIR`)
- `services/gemini/` — Gemini package (post-NARR-5): `client` + `audio` (WAV-Concat, **geteilt** mit `narration_render`/`google_tts_service`) + `voices` (Gemini-TTS-Voice-Katalog, reine Daten). `GeminiService` (via `__init__.py`) ist **dormant** — der Alt-Podcast-Flow, der es trieb, ist weg; Klasse + `gemini_service`-Singleton bewusst stehen gelassen (Seam für ein künftiges Gemini-Text-Feature)
- `services/deepgram_service.py`, `services/google_tts_service.py`, `services/narration_render.py`, `services/narration_library.py`, `services/audio_chunker.py`, `services/pdf_extraction/`
- `tasks.py` — RQ background tasks (narration rendering: `generate_narration_task`)
- `worker.py` — RQ worker process
- `models.py` — SQLAlchemy models (User, ConversionHistory)
- `tests/` — Characterization tests (~37 tests, ~5s); mocks at SDK-singleton boundary so they survive future service splits
- `static/js/` — Per-feature JS modules + shared `_utils.js` (Helper: `showAlert`, `showToast`, `formatFileSize`); templates inline only small `window.PageData = {…}` blocks
- `static/css/style.css` — Single stylesheet with TOC + section comments (not split by design)

## Architecture Notes
- Narration generation is async: the web enqueues an RQ job via Redis, the worker renders the WAV onto the shared `podcast_data` Docker volume, the frontend polls `GET /api/narrations/<id>` until ready. Long transcripts are byte-chunked in `services/narration_render.py` (eigene Logik) und mit pydub/wave konkateniert. Details im Faithful-Narration-Bullet unten. (Der alte unkontrollierte Podcast-Generierungs-Flow wurde in NARR-5 stillgelegt.)
- **Routing pattern:** route modules in `app_pkg/` expose a `register(app)` function rather than Flask `Blueprint(...)` objects, to keep endpoint names flat. New routes must follow the same pattern.
- **Service-singleton pattern:** SDK clients (`deepgram_service`, `gemini_service`, `google_tts_service`, `task_queue`, `async_playwright`, `partition`) are bound at the top level of `app.py` so tests patch them at `app.<name>`. New SDK integrations must follow this convention or update test patches.
- **Faithful-Narration (NARR) — `audio_narration`-Flow:** treue Dokument-Vertonung via Cloud-Gemini-TTS (`services/narration_render.py`, s. *Gemini Models* oben), agent-getrieben. **POST `/api/narrations`** (`app_pkg/narration.py`) ist token-authed über **`NARRATION_TOKEN`** — ein **eigener** Token (nicht `CARD_TOKEN`-geteilt: Narration kostet GCP-Geld pro Call → unabhängig revozierbar), **fail-closed wie `CARD_TOKEN`** (503 ohne Token, constant-time 401), CSRF-exempt; `_authorize_card_write` ist **gespiegelt** (cards.py unberührt), `_bearer_token`/`_resolve_target_user` aus `app_pkg.ingest` wiederverwendet. Der POST legt eine **`pending`**-Conversion an (`conversion_type='audio_narration'`, Audio-Felder in `metadata_json` — **kein** Schema-Touch) + enqueued `tasks.generate_narration_task`. **⚠️ Option B — Worker DB-frei:** der Worker-Container mountet `podcast_data`, **nicht** `app_data` → der Worker rendert nur (`narration_<id>.wav` aufs geteilte Volume) + returnt, **flippt KEINE DB**; die **Web-Seite rekonziliert** (`reconcile_narration`, **file-first**) `pending`→`ready`+Dauer / `failed`+error beim Pollen (`GET /api/narrations/<id>`) **und** beim Serve (`GET /api/narrations/<id>/audio`, vor dem ready-Gate). Transienter Redis-Fehler → bleibt `pending` (kein Fehl-Fail), Terminal-States idempotent. **Library-Player (NARR-5):** `library_detail.html`/`library_detail.js` zeigen für `audio_narration` einen Audio-Player über dem Transkript-Reader (pollt `/api/narrations/<id>`: `ready`→`<audio>` + Dauer/Stimmen, `pending`→Spinner, `failed`→Fehler + Retry). **`POST /api/narrations/<id>/retry`** ist **Session**-authed (CSRF-geschützt, kein Token, kein Agent-Call), owner-/type-404, **failed-only** (sonst 409), re-enqueued `generate_narration_task` aus den **gespeicherten** Render-Inputs (`metadata.transcript`/`speakers`/`mode`/`style_prompt`/`language_code`/`tts_model` — NARR-5 persistiert mode/style/language mit, Pre-NARR-5-Rows fallen graziös zurück). **Sprach-Code (NARR-FAIL):** `language` muss ein **regionierter BCP-47-Code** sein (`de-DE`) — Gemini-TTS-Voices **400t** bei nacktem `de`; `_normalize_language_code` (an POST **und** Retry, geteilter Helper) mappt nackt→regioniert (`de→de-DE`, `en→en-US`), reicht Regioniertes durch, unmappbar→400. ⚠️ Am Retry ist die Normalisierung **load-bearing**: der gespeicherte Code läuft durch `or DEFAULT`, ein truthy-aber-falscher `'de'` umginge den Default — ohne Normalisierung failt der Retry identisch. `reconcile_narration` speichert bei Fehler den Traceback-**Tail** (`exc_info[-2000:]`, nicht Head — die Exception-Zeile steht am Ende). Details: [docs/narration_reframe.md](docs/narration_reframe.md).
- **Audio-Transkription + Sprecher-Erkennung (DIARIZE) — `audio_transcription`-Flow:** [services/deepgram_service.py](services/deepgram_service.py), Deepgram `nova-3`. **Diarization ist immer an** (kein UI-Toggle) via **`diarize_model="v2"`** — durchgereicht als `request_options["additional_query_parameters"]` (das gepinnte SDK **`deepgram-sdk==7.1.0`** kennt **keinen** typisierten `diarize_model`-kwarg, nur `diarize: bool`=altes v1). ⚠️ **NIE `diarize=true` daneben** — Requests mit beiden Params werden von Deepgram rejected. Pure `format_diarized_transcript(utterances, plain_transcript)`: ≥2 distinct Sprecher → `**Sprecher N:**`-Markdown-Blocks (konsekutive gleiche Sprecher konsolidiert, 1-basierte Anzeige aus 0-basiertem API-Index); **Single-Speaker-Guard** — genau 1 Sprecher **oder** `utterances` leer/`speaker=None` → `plain_transcript` **byte-gleich** (Olis Einzel-Diktate ändern sich null; Diarization-Ausfall bricht die Transkription nie). **Chunk-Schwelle `MAX_AUDIO_DURATION_SECONDS=5400` (90 min):** ≤90 min = **1 Request** = Chunk-übergreifend konsistente Sprecher (`TIMEOUT_DEEPGRAM_SECONDS=1200` trägt den Upload, bleibt unter gunicorn-1800s). >90 min → Chunk-Pfad läuft `_transcribe_single(apply_diarization=False)` = Plain wie vor DIARIZE (per-Chunk-Sprecher inkonsistent + Präfixe würden den Overlap-Merger stören) **+** ein vorangestellter Degradations-Hinweis; Merger unberührt. Echte Sprecher-Namen macht **nachgelagert** der `notion-transcripts`-Agent aus den generischen Labels. Dokumentierter Fallback bei ungenügender v2-Qualität: AssemblyAI (eigener Sprint, **nicht** gebaut).
- **Send-to-Kindle (KINDLE):** ein Library-Element geht als **EPUB** (via `ebooklib`, gebaut aus dem geteilten `render_markdown_to_html`) per **Send-to-Kindle-E-Mail** (stdlib `smtplib`, einziger programmatischer Pfad — keine API) raus; SMTP-Config + **server-fester** Empfänger (`KINDLE_TO_EMAIL`, Anti-Relay) aus `.env`, **fail-closed wie `CARD_TOKEN`**. Details: [docs/kindle.md](docs/kindle.md). `services/epub_service.py` + `services/kindle_service.py` sind pure Module (kein SDK-Singleton), Tests mocken den SMTP-Transport. **Math im EPUB (KINDLE-MATH):** beim Bau läuft ein server-seitiger LaTeX→MathML-Pass (`services/epub_math.py`, pure-Python `latex2mathml`) über die `math-inline`/`math-display`-Spans **bevor** sie EPUB3-Chapter werden (E-Reader führen kein JS → KaTeX greift nur in Reader/Preview/PDF); flag-gegated via `EPUB_MATH_MODE` (Default `mathml`, `off`=Kill-Switch, `image`=dokumentiert-aber-ungebauter Bild-Escape-Hatch); per-Gleichung try/except (latex2mathml **wirft** → Fallback auf sichtbaren Roh-LaTeX-Span); OPF-Property via `chapter.properties.append('mathml')` (Attribut-Form, **nicht** Konstruktor-kwarg).
- **Learning/Review (LEARN-UP, 2026-07-18) — `/review` + `app_pkg/learn.py`:** Die Queue-Ordnung passiert **Python-seitig pro Fetch** in `learn.order_due_cards` (kein DB-`ORDER BY` mehr): `smart` (Default) = **FSRS-Retrievability aufsteigend** via additivem `FSRSScheduler.retrievability` (Basisklasse liefert `None` — SM-2 reused `stability` als Interval-Tage, nie in die R-Formel füttern; ⚠️ py-fsrs rechnet R **tages-granular** → der Shuffle-vor-Stable-Sort-Tiebreak ist load-bearing) + Neu-Karten (stability NULL) in **Erstellungsreihenfolge** (seit LEARN-QUEUE, s.u.) und per Fractional-Merge gleichmäßig eingestreut; `random` = Voll-Shuffle. **Study-Sets = Sammlungen**: der Launcher sind Checkbox-Pills mit Fällig-Badges (`due_count` roh `Review.due<=now` aus `/api/collections`), Mehrfach-Auswahl = Union (`?collection=1,2`, EXISTS-dedupliziert, owned-oder-404); **Tags sind raus aus dem Lern-View** (der `?tag=`-Param besteht Backend-only; `/tags`-Manager + Agent-Tag-Pfade unberührt). **Settings** leben in EINEM `User.settings_json`-Blob (lenient read / strict write über `GET/PUT /api/learn/settings`): `ordering_mode`, `daily_new_limit` (10), `daily_review_limit` (200). **Daily-Limits** cappen **nach** Ordering (wackligste/zufällige N) mit tages-korrekter Zählung: `count_done_today` zählt Karten mit `last_reviewed` im **Berlin-Lokaltag** (geteilter Helper `local_day_bounds`; Dep `tzdata` als zoneinfo-Fallback), Klassifikation neu-vs-Review am ersten `rating_history`-Eintrag; neue Karten füllen nur das Review-Headroom. **Stats**: `GET /api/learn/stats` (Heute-Zahlen == Launcher **by construction** via geteiltem `capped_session_counts` · 28-Tage-Forecast nach Berlin-Tagen + Rückstand-Marker · Reifegrad neu/jung/reif ab 21-Tage-Intervall, „lernend" bewusst in jung kollabiert · True-Retention aus `rating_history`, Intro-Tag exkludiert, 30-Tage-Fenster, gegen **read-only** aus env surfaced `desired_retention` — es user-editierbar-wirksam zu machen wäre ein Scheduler-Vertrags-Umbau) + `GET /api/learn/simulate` (Expected-Value-Kohorten-**Schätzung** in `fsrs_scheduler.simulate_workload`; py-fsrs hat keinen Simulator; What-if-Retention ist reiner Input, der echte Scheduler bleibt env-gesteuert). **Ein Lernschritt (LEARN-STEP, 2026-07-25):** `FSRSScheduler` setzt `learning_steps=(10 min,)` + `relearning_steps=(10 min,)` **explizit** — py-fsrs' geerbter Default `(1 min, 10 min)` zeigte jede neue Karte am ersten Tag zweimal, auch nach korrektem „Gut" (exakt zweimal, nie öfter: `_reconstruct` baut Karten mit `stability` als `State.Review`, die Leiter greift nur beim allerersten Rating). Ein Schritt: neu+Gut/Einfach → mehrtägig (für den Tag erledigt), neu+Nochmal/Schwer → 10/15 min (kommt in der Session wieder — gewollt); Sentinel-Test in [tests/test_scheduler.py](tests/test_scheduler.py) nagelt beide Step-Listen fest, damit ein py-fsrs-Bump mit geänderten Defaults laut wird statt still das Lernverhalten zu verschieben. Bewusst **kein** Env-Regler (Lern-Doktrin, kein Betriebsparameter). **„Mehr lernen" gestuft (LEARN-MORE, 2026-07-26):** `/api/review-state` kennt zwei **strikt** gelesene Session-Parameter — `?uncapped=1` (nur der exakte Wert schaltet) hebt die Tages-Caps für diesen Fetch auf; `?ahead=<1..7>` verschiebt die Fälligkeitsgrenze auf das Ende des Berliner Tages `heute+n` via `learn.local_day_end` (impliziert uncapped; 0/8/abc → 400). **Wiederholungsfrei per Konstruktion**: die Queue ist `due <= Horizont`, heute Erledigtes trägt ein Zukunfts-due und kann nicht zurückkommen — deshalb braucht „mehr lernen" keinerlei Session-Gedächtnis. Drei Antwort-Felder: `remaining_today` (jetzt Fällige, die der Cap zurückhielt; 0 bei uncapped), `next_ahead` = `{days, count} | null` — der **nächste Tag, der tatsächlich Karten hat** (Lückentage werden übersprungen; die Progression ist komplett **server-getrieben**, das UI klickt nur mit dem gelieferten `days`-Wert; Deckel `MAX_AHEAD_DAYS=7`, am Max/außer Reichweite → null), `day_end` (heutiges Berliner Tagesende, zeitzonen-behaftet). **UI** ([static/js/review.js](static/js/review.js)): genau EIN Angebot im Done-Panel — Stufe 1 „Mehr lernen" (Überhang) vor Stufe 2 „Morgen vorziehen"/„Vorziehen" (Microcopy benennt Borgen + Preis); Stufe 2 nie ohne eigenen Klick. Session-Geste nur im Modul-State (Seiten-Reload startet gecappt — Nicht-Ziel), Scope-/Settings-Wechsel resettet sie. Queue leer **nur wegen Cap** → Done-Panel „Tagespensum erreicht." + Stufe 1 (sonst wäre der Überhang nach jedem Reload unerreichbar). Am **komplett leeren Tag bewusst kein Vorzieh-Angebot** — das ist Lern-Entscheidung, nicht Lücke: keine fällige Karte heißt, der Scheduler sagt Stopp, ein Vorzieh-Knopf dort arbeitete gegen ihn (Anki versteckt „review ahead" aus demselben Grund hinter Custom Study); das Done-Panel ist der legitime Ort, weil dort gerade gearbeitet wurde. **Angebots-Zahlen veralten einseitig — das ist eine Garantie, kein Makel**: Bewertungen während der Session können `remaining_today`/`next_ahead.count` nur wachsen lassen, nie schrumpfen — das Angebot verspricht nie Karten, die es nicht gibt; der Klick lädt Server-Wahrheit. **`stillDue` vergleicht gegen `day_end`**: „Karte verlässt den Pool, wenn ihr neues due hinter dem heutigen Berliner Tagesende liegt" — naive-UTC-dues werden via `parseUTC` gepinnt, das JS macht **keine** Zeitzonen-Arithmetik mehr (löst die LEARN-COUNT-Zufalls-Korrektheit aus Memory `reference_naive_utc_due_js_local_parse` auf). Master-Entscheidung, die Oli nach erstem Gebrauch kippen kann: **Stufe 2 borgt tageweise** (ein Tag pro Klick, `next_ahead`-Progression). **Neue Karten in Erstellungsreihenfolge (LEARN-QUEUE, 2026-07-30):** im `smart`-Pfad sortiert `order_due_cards` den `fresh`-Topf nach `created_at` asc mit `id` als Tiebreak (`_fresh_sort_key`) statt ihn zu shufflen — der Agent legt Karten im Batch an, Zeitstempel kollidieren, und eine nicht-totale Ordnung wäre wieder nicht reproduzierbar. Grund ist **Didaktik**, nicht Vorhersagbarkeit: der Karten-Autor schreibt Material in einer Reihenfolge (erst die Tabelle, dann die Tendenzen), ein Shuffle warf sie weg und würfelte die Queue bei jedem Abruf neu. ⚠️ Das revidiert die LEARN-UP-Aussage „die versteckte Erstellungsreihenfolge ist strukturell weg" **nur für neue Karten** — für **Wiederholungen** (deren Root Cause `ORDER BY due ASC` über alles war) gilt sie unverändert, R-Sortierung samt Zufalls-Tiebreak bleibt unangetastet, und `random` bleibt Voll-Shuffle (die Einstellung heißt so). Erwünschte Folge: der Neu-Cap schneidet die **ältesten** N heraus statt zufälliger N (Kapitel 4 wird fertig, bevor Kapitel 5 anfängt). ⚠️ **Sammlungsübergreifend ordnet das nach Alter der Sammlung** — bei Oli BI-Pipeline (22.06.) → Plant & Process (28.06.) → TCE (29.06.) → Chemie-Basics (29.07.): innerhalb einer Sammlung ist das die gewünschte Kapitelreihenfolge, im ungescopeten „Alles fällig" heißt es, dass sein **aktuell aktives** Material unter den neuen Karten zuletzt kommt (und die per LEARN-BACK zurückgesetzten TCE-Karten behalten ihr altes `created_at`). Das ist **kein Fehler**, sondern die direkte Folge der Entscheidung; die Antwort darauf ist die Sammlungs-Pille. **Waisen-Pille (LEARN-QUEUE):** `/api/review-state` kennt zusätzlich **`?uncollected=1`** (strikt gelesen wie die LEARN-MORE-Parameter) = Karten in **keiner** Sammlung. Es **unioniert** mit `collection=` statt es zu ersetzen (`or_(Card.collections.any(...), ~Card.collections.any())`) — die Pillen sind Mehrfach-Auswahl, „Sammlung X **oder** ohne Sammlung" ist die einzige Semantik, die zum Modell passt; ⚠️ der `?tag=`-Filter bleibt **außerhalb** der Disjunktion (Tag AND (Sammlung OR Waisen)), sonst würde aus dem AND still ein OR. Die Zahl reist als **`uncollected_count`** in der review-state-Antwort — roh `due <= now` wie die Sammlungs-Badges und **global aus einer eigenen Query, nicht aus `base`**: ein Zähler, der die Sichtbarkeit seines eigenen Schalters steuert, darf nicht im Scope liegen, den der Schalter setzt (gescopet wäre er 0, sobald eine Sammlung angehakt ist, und die Pille verschwände genau beim Umschalten). ⚠️ **`/api/collections` bleibt unangetastet** — es liefert ein **blankes Array**, das die iOS-App als `[LearnCollection]` dekodiert; ein Objekt-Wrapper oder ein synthetischer Eintrag mit `id: null` bräche sie, additive Felder auf `review-state` sind dagegen nachweislich unschädlich. Folge, bewusst: **die Pille gibt es auf iOS nicht** (deren Scope-UI baut auf `/api/collections`) — falls gewünscht, ist das ein eigener Sprint. **UI**: Pille „Ohne Sammlung" hinten in der Reihe (sie ist der Rest, kein Study-Set), **nur gerendert wenn `uncollected_count > 0`**; die Invariante „Pille existiert gdw. Zahl > 0" wird in `renderScopePills` durchgesetzt (`if (uncollectedCount <= 0) scopeUncollected = false`), weil das die eine Stelle ist, die sie kennt — sonst überlebte ein angehakter Waisen-Scope als Filter, den niemand mehr abwählen kann. Ordnet man die Waise per Fuß-Panel einer Sammlung zu, wandert ihr Roh-Zähler mit **und** `card.collections` wird lokal nachgeführt: `decrementPoolCounts` liest genau dieses Feld, ohne die Nachführung senkte das spätere Bewerten den Waisen-Zähler ein zweites Mal.
- **Abbildungen auf Lernkarten (CARD-SVG, 2026-07-25):** `Card.front_svg`/`back_svg` (`db.Text`, Auto-Migration) tragen agent-geschriebenes **SVG-Markup** — kein Asset-Store, kein Upload, kein Bild-Format; Autoren-Pfad ist **nur der Agent** (zwei optionale Felder an `POST /api/cards` + `PATCH /api/cards/<id>`, `string|null`, Leeren via `null`/`""`), **keine** Edit-Fläche im Review. **Eigener Sanitizer mit eigener Allow-List**: [services/svg_sanitize.py](services/svg_sanitize.py) ist pur (nur `re`+`nh3`), importiert **nichts** aus [app_pkg/markdown_render.py](app_pkg/markdown_render.py) → **null Blast-Radius** auf PDF/EPUB/Library/Reader; **kein `'*'`-Wildcard, kein `style`, kein `class`** (letzteres gewährt nichts, kollidiert aber mit den App-Utilities — `class="hidden"` träfe genau die Klasse, mit der `review.js` die Figuren versteckt). - **Rating-Semantik (LEARN-RATE, 2026-07-29) — die Knöpfe sagen, was sie meinen:** In 122 Bewertungen über drei Sessions fiel **0×** „Wieder" (69× Schwer, 53× Gut, 0× Leicht); auf die Rückfrage, was „Schwer" für ihn heißt, antwortete Oli *„kaum bis gar nicht gewusst."* Der Scheduler bekam damit systematisch `hard` (bestanden, Stabilität wächst) wo `again` gehört (Lapse, Relearning, Stabilität bricht ein) — gemessen gegen `fsrs==6.3.1` mit Olis echten Rating-Abständen: `again`/hard/hard → **7 Tage**, `hard`/hard/hard → **15 Tage**, der Beschriftungsfehler allein **verdoppelt das Intervall**. Nebenwirkung: `true_retention` zählt `again` als Fehlschlag → bei null `again` meldete die Statistik **100 % Behaltensrate**. **Ursache war das Label, nicht der Nutzer**: `Wieder` steht als Adverb ohne Bezugswort und benennt keinen Ausgang, die Reihe liest sich als reine Schwierigkeitsskala, in der „Schwer" für „kaum gewusst" die folgerichtige Wahl ist. **Doktrin seit dem Fix — die Entscheidung ist zweistufig und steht auch so da:** über der Reihe die Frage *„Wusstest du die Antwort? Nur wenn ja: wie mühsam?"*, darunter `Nochmal` (nicht gewusst) · `Schwer` (gewusst, mühsam) · `Gut` (gewusst) · `Leicht` (sofort da). Die Bedeutungen sind **bewusst asymmetrisch** — nur Knopf 1 beschreibt einen **Ausgang**, 2–4 beschreiben **Aufwand**; diese Bruchkante ist die Botschaft und darf nicht glattgezogen werden. Bedeutung + Tastenziffer sitzen **im** Knopf (kein Tooltip/Hover — Touch kennt kein Hover; als Geschwister daneben wäre die Trefferfläche zerschnitten), `aria-label` trägt Label **und** Bedeutung. `data-rating`, das Kürzel-Mapping 1–4 und [static/js/review.js](static/js/review.js) sind **unverändert** — der Delegations-Klick läuft über `closest('.review-rate-btn')` und trägt die verschachtelten Spans. **Breakpoint 560 px ist gemessen, nicht gerundet** (`@media (max-width: 559.98px)` → 2×2 statt vier nebeneinander): bei 375 px blieben je Knopf **53 px** Textbreite, allein „Nochmal" braucht **57 px**, „gewusst, mühsam" 49 px — vier gestapelte kosteten ~248 px Höhe und schöben die Bewertungsleiste unter die Falz (derselbe Fehler, den der 32vh-Deckel aus CARD-SVG schon korrigiert), 2×2 kostet ~164 px bei 119 px Trefferfläche. Secondary misst 4,14:1 (light) / 5,54:1 (dark) — dark ist AA, **light liegt knapp unter dem 4,5:1-Schwellwert** (`--text-xs`/`--text-sm` fallen nicht unter die Large-Text-Ausnahme); bekannt, kein Blocker, die nächste Stufe wäre `--nm-text` für die Bedeutungszeile allein. Die Ziffern bleiben muted. **Eine Portierung (iOS) darf nicht wieder über muted gehen.** **Die Suite deckt das nicht ab** — keine Template-/CSS-Renderung, `pytest` blieb bei 762 unverändert grün; der Gate war der Live-Smoke (Desktop + 375 px × dark/light, Tasten 1–4, Klick auf jeden Knopf inkl. Kind-Spans, server-seitig in `rating_history` gegengeprüft).
- **Intervall-Regler (LEARN-TUNE, 2026-07-30) — zwei ehrliche Betriebsparameter, kein Eingriff in die Mathematik:** Beide Regler sind **Env-only** (wie `desired_retention` seit R4-LEARN), **FSRS-only** (SM-2 kennt kein `maximum_interval` — im `FSRSScheduler`-Docstring als „keine Symmetrie herstellen" markiert) und wirken **ausschließlich auf künftige Bewertungen** — keine bestehende Karte wird umgesetzt. `FSRS_DESIRED_RETENTION` (Default 0,9) und neu `FSRS_MAXIMUM_INTERVAL` (Default **36500** = py-fsrs' eigener Default = aus → **ohne gesetzte Variable ist der Sprint verhaltensneutral**, per Assertion festgenagelt); `_parse_max_interval` ist gebaut wie `_parse_retention` (nicht-int / ≤ 0 / leer → still Default, wirft nie) und liegt in [services/scheduler/fsrs_scheduler.py](services/scheduler/fsrs_scheduler.py) statt neben `_parse_retention` im Package-`__init__`, weil `simulate_workload` denselben Parser braucht und nicht aufwärts importieren kann (Zirkel) — beides wird im `__init__` re-exportiert. **Der Simulator clampt mit** (`simulate_workload(..., maximum_interval=None)` → dieselbe Env, derselbe Parser wie `get_scheduler()`): Projektion und Scheduler deckeln bei demselben Wert, sonst versprach die Vorhersage Intervalle, die der Scheduler nie ausgibt — dieselbe Drift, die LEARN-UP für die Heute-Zahlen mit `capped_session_counts` ausgeschlossen hat. **⚠️ Ein Deckel HEBT die Last** (kürzere Intervalle = mehr Reviews pro Karte und Jahr) — die Master-Vorgabe stand hier verkehrt und wurde nach der Messung revidiert; gemessen mit `simulate_workload` bei 24 neuen Karten/Tag und Retention 0,92: **aus 141 · 120 → 144 · 90 → 158 · 60 → 188 · 21 → 400** Reviews/Tag, zu lesen gegen `daily_review_limit` (200). **Deploy-Werte: `FSRS_DESIRED_RETENTION=0.92` + `FSRS_MAXIMUM_INTERVAL=120`** (Oli). **Warum nicht 60**: Olis TCE-Karten trugen Stabilität 11,7–56,6 Tage — ein 60-Deckel hätte **keine einzige** beschnitten, aber die Last auf 94 % seines Limits gehoben und damit den Regelkreis gestartet, gegen den er gesetzt war (zurückgehaltene fällige Reviews werden überfällig → überfällig-dann-gewusst bläht Intervalle). Die Prüffrage vor jedem Guard Rail ist deshalb, **ob er den Fall überhaupt erwischt hätte, der ihn motiviert hat.** **Der Deckel greift am Intervall, nicht am Modell:** am gedeckelten Review ist die Stabilität **identisch** (gemessen, 162,9 mit und ohne Deckel — als Test festgenagelt); danach wächst sie langsamer, aber nur weil die Karte **wirklich** früher wiederkommt — FSRS sieht weiter die echte verstrichene Zeit, nur eine kürzere. **Genau deshalb wurde kein Eingriff in `elapsed_days` gebaut:** py-fsrs bietet keinen Hook, es würde dem Modell dauerhaft falsche Daten unterschieben, und die Prämisse „die App verursachte den Verzug" ist widerlegt (die Tages-Caps kamen mit LEARN-UP am 18.07., Olis Lücke war 01.07.→18.07.). Nicht gebaut außerdem: **kein Optimizer-Lauf** (bräuchte torch, das IMG-SLIM gerade aus dem Image geworfen hat, und ~1000+ Bewertungen — bei 122 wäre es Kurvenanpassung an Rauschen) und **kein Umsetzen bestehender Karten**.
- **Karten zurücksetzen (LEARN-BACK, 2026-07-30) — `flask reset-collection <name|id> [--apply]`:** Einmalige Korrektur **vergifteter** Scheduling-Daten, **kein wiederkehrendes Werkzeug** — deshalb ein CLI-Kommando neben `create-user` ([app_pkg/__init__.py](app_pkg/__init__.py)) und **kein** Endpoint, **keine** UI, **keine** Agent-/Token-Fläche; ein Per-Karte-Reset-Knopf im Review wäre ein eigener, bedarfsgetriebener Sprint. Umdatieren hätte die Fälligkeiten zusammengezogen, aber das Phantom-Modell mitgeschleppt — **wenn die Semantik der Eingabedaten ungültig war, ist Zurücksetzen ehrlicher als Umdatieren** (Preis: 40 Wiedereinführungen, bewusst akzeptiert). Zwei gesperrte Entscheidungen: (1) die `Review`-Zeile wird **feldweise aus `initial_review_state()`** ([services/scheduler/base.py](services/scheduler/base.py)) gesetzt — es gibt genau **eine** Definition von „neu" (beide Engines geben sie aus `new_card_state()` zurück, `POST /api/cards` schreibt sie), eine nachgebaute Feldliste liefe bei der nächsten Scheduler-Änderung still auseinander; (2) **`rating_history` wird geleert** — die Einträge tragen die ungültige Semantik, `count_done_today` klassifiziert neu-vs-Review am **ersten** Eintrag (stehengelassen zählte die wiedereingeführte Karte gegen das **Review**- statt das Neu-Budget) und `true_retention` schleppte die falsch gemeinten Bewertungen noch ~30 Tage weiter; der Audit-Trail ist der Preis, sein Wert war durch die Semantik ohnehin zerstört. Auswahl ist `stability IS NOT NULL` (nur bereits Bewertetes) ⇒ **per Konstruktion idempotent**, der zweite Lauf findet 0 Zeilen. **Dry-run ist Default**, `--apply` schreibt (Hauspattern `scripts/cleanup_tags.py`); Sammlung per Name **oder** id, über User hinweg mehrdeutiger Name → Fehler statt Vermutung; Überschneidungen mit anderen Sammlungen werden **vor** dem `--apply` benannt. ⚠️ **`due` läuft durch `_naive_utc`** (aus `app_pkg.cards`, lokaler Import — top-level wäre zirkulär): `initial_review_state()` liefert **aware** UTC, die Spalte hält **naive**, und SQLite wirft das `tzinfo` still weg — ohne den Konverter wäre der Pfad nur zufällig richtig (die Wanduhr von `datetime.now(timezone.utc)` *ist* die naive UTC) und eine spätere Zonen-Umstellung träfe allein diesen einen Schreibweg. Karteninhalte, Tags und Sammlungen bleiben unberührt.

## Auth

- **Web-UI**: Flask-Login-Session-Cookie (`POST /login`, Formular) + globales CSRF. Mechanisch läuft CSRF seit MOBILE-AUTH über die **Inversion** (unten) — das Verhalten für Session-Requests ist byte-identisch zu vorher.
- **Native App (MOBILE-AUTH)**: `POST /api/auth/login` (JSON, public, CSRF-exempt) → **per-User-Bearer-Token**; die App sendet `Authorization: Bearer <token>` auf allen `/api/...`-Reads **und** -Writes, ohne Cookie/CSRF. `GET /api/auth/me` validiert einen gespeicherten Token, `POST /api/auth/logout` revoked die präsentierte Row. Kontrakt für den iOS-Agenten: [docs/mobile_auth_contract.md](docs/mobile_auth_contract.md).
- **Erster identitäts-tragender Token**: `ApiToken`-Tabelle (`models.py` — sha256-Hash unique, Klartext genau einmal in der Login-Response, Revoke = Row-Delete, `expires_at` optional/NULL) — **distinct** von den drei write-only-single-user Env-Tokens (`INGEST/CARD/NARRATION_TOKEN`), die unberührt weiterlaufen.
- **Bearer-Identität** via `login_manager.request_loader` (`app_pkg/__init__.py`): **alle** `@login_required`-Views akzeptieren den Token ohne Per-View-Änderung; Session/Remember-Cookie haben Loader-Vorrang, der Web-Pfad konsultiert den request_loader nie. Login-Fehler + kaputte/widerrufene Tokens → **generisches 401** (Anti-Enumeration: Dummy-`check_password_hash` bei unbekanntem User, identische Response-Bodies); Tokens erscheinen nie in Logs.
- **CSRF-Inversion** (`_register_csrf_inversion`, `app_pkg/__init__.py`): `WTF_CSRF_CHECK_DEFAULT=False` + eigener `before_request`, der `csrf.protect()` explizit für Cookie-Session-Mutationen aufruft und bei Bearer-Header-**Präsenz** überspringt (Gültigkeit prüft die Auth — ungültiger Bearer stirbt fail-closed mit 401). ⚠️ Der Handler **repliziert die Guard-Kette von Flask-WTF==1.2.1** (`WTF_CSRF_ENABLED` → Methode → Exempt-Blueprints/-Views → `protect()`), weil `csrf.protect()` selbst nur die Methode prüft und `_exempt_views` privat ist — **bei jedem Flask-WTF-Bump gegen Upstream re-verifizieren** (Sentinel-Tests in `tests/test_csrf_inversion.py` schlagen bei Bruch an).
- **`unauthorized_handler`**: 401-JSON **nur** wenn Bearer-Header präsent oder Pfad unter `/api/auth/` — jede Cookie-Web-Anfrage behält den 302-Redirect (die `_utils.js`-`safeJSON`-„Session expired"-UX hängt an `response.redirected`).

## Working Practice — Master = Dispatch, Sub-Thread = Execute

**Prinzip in einem Satz**: Master-Thread plant, pflegt Backlog, schreibt Sprint-Prompts. Sub-Thread pro Sprint führt aus. **Master macht keine Code-Edits.**

**Arbeitsort & Deploy (wichtig — sonst Split-Brain)**: Mac-lokal `/Users/olivergluth/CODE/CONVERTER` ist **Source-of-Truth** — alle Master- und Sub-Thread-Arbeit (Edits, Commits, `git status`) passiert hier, gegen `origin` (GitHub). Der Mintbox-Mount `/Volumes/MintHome/CODE/CONVERTER` ist **nur Docker-Runtime, nie Arbeitsplatz** (er zeigt zudem einen spurious 0-change-dirty-tree — Memory `reference_two_clone_coordination_mac_mintbox`). **Deploy**: auf der Mintbox `git pull` von origin + `docker compose up -d --build` (Templates sind ins Image gebacken → `--build`, nicht `restart`); nie direkt in den Mount editieren.

**Mechanik**:
1. Master schreibt Sprint-Prompt-Doc unter `docs/archive/sprint-prompts/SPRINT_<CODE>_<NAME>_<datum>.md` — imperativ, in Phasen geschnitten, Stop-Regel nach jeder Phase.
2. Master liefert **direkt im Chat einen copy-paste-fähigen Anfangs-Prompt** in folgendem Format:

   ```
   Du übernimmst den Sub-Thread für Sprint <CODE> (<KURZ-TITEL>).

   Sprint-Prompt vollständig lesen: <ABSOLUTER-PFAD-ZUR-SPRINT-DOC>

   Dann Phase 1 direkt starten — nicht zusammenfassen, nicht planen, nicht beurteilen. Sprint-Prompt = ausführen. Master macht Dispatch, du machst Execute. Nach jeder Phase Stop + Bericht.

   Working-Practice in /Users/olivergluth/CODE/CONVERTER/CLAUDE.md unter Sektion "Working Practice".
   ```

   Kein `cat ... | pbcopy`-Indirection-Schritt mehr — der direkte Prompt-Block pinnt den Sub-Thread auf Executor-Rolle und verhindert das „lies und plane"-Missverständnis.
3. Oliver kopiert den Block aus dem Chat, öffnet einen frischen Sub-Thread, paste-t.
4. Sub-Thread arbeitet Phasen ab, berichtet zwischen Phasen, wartet auf Sign-off.
5. Sub-Thread pflegt am Ende STATUS.md + BACKLOG.md + ggf. Memory.
6. Master nimmt Stand-Update zurück und schreibt nächsten Sprint-Prompt.

**Master-erlaubte Edits** (Dispatch-Artefakte, kein Code):
- `CLAUDE.md`, `STATUS.md`, `BACKLOG.md`
- `docs/archive/sprint-prompts/SPRINT_*.md`, `_TEMPLATE.md`, `README.md`
- Hand-off-Doc (`MASTER_BACKLOG_HANDOFF_<datum>.md`) beim Master-Wechsel
- Memory-Zone (`feedback_*.md`, `reference_*.md`, `MEMORY.md`)

Alles andere — Feature-Code, Templates, Tests, Services — gehört in einen Sprint.

**Disziplin**:
- Master sagt nie „mach jetzt einfach". Bei Frust: max. 1 Klärungsfrage, dann Sub-Session.
- Sprint-Prompt-Doc ist Ausführungs-Doku, nicht Diskussions-Doku. Review/Diskussion ist ein eigener Sprint.
- Phase 0 (Workshop / Mechanik-Fragen) ist **Ausnahme**, nicht Default — nur wenn echt eine Mechanik-Wahl offen ist. Triviale Sprints starten direkt in Phase 1.
- BACKLOG.md = Source-of-Truth offene Items. STATUS.md = aktueller Stand.
- Parallele Sprints sind erlaubt, solange ihre Backlog-Items disjunkt sind.

**Sprint-Sizes**: S/M/L/XL — Daumenregel: S = ein File-Touch, M = ein Feature-Cluster, L = mehrere Features, XL = Schema/Migration. Größer als L → splitten.

**Bootstrap für neuen Master-Thread**: lies `CLAUDE.md` → `STATUS.md` → `BACKLOG.md` → ggf. `MASTER_BACKLOG_HANDOFF_<datum>.md` (sofern vorhanden). Dann Sprint-Prompt schreiben.
